# CPEA 實驗與架構選型決策紀錄規格

> **狀態：**規格待確認；未產生實驗判定或架構選型結論。原始歷史 Raw／FAIL／Task 狀態不可改寫。

本規格適用 R1 的實驗裁定、R2 可行性、ADG-01 架構設計決策及 R3 的架構回饋。搭配 [研究規格](ab-evaluation-plan.md) 與 [任務依賴](task.md)；決策產物寫至未來新 run 的受保護目錄，公開計畫只保留安全引用。本次不建立結果目錄。

## 紀錄共通欄位

| 欄位 | 必要內容 |
| --- | --- |
| 身分與狀態 | 唯一 `decision_id`、所屬 task／experiment／run、紀錄版本、`proposed|reviewed|accepted|superseded`、建立／審核時間、作者與獨立 reviewer |
| 問題與範圍 | 要決定的能力、scope／mode／案例分組／方言；不在本次證據可證明範圍的能力 |
| 基準與候選 | A0 或現有架構、候選 strategy／adapter／套件／模型 ID／版本、比較責任、不可比項及理由 |
| 輸入來源 | 原文／catalog／schema／prompt／上游／Prepared Task／semantic model／fixture 指紋、核准效力、是否 injected、額外人工知識 |
| 可重現證據 | Git SHA／worktree／dirty diff、完整性 manifest、首次 Raw／Normalized／plan／SQL 引用與 hash、實際命令／退出碼／環境、Replay 或 regrade 類型及結果 |
| 通過與失敗 | 每題六層 verdict、逐 requirement 義務、首錯與附帶錯誤；成功、FAIL、pending、unsupported、skipped、unfinished 及未測均列出，至少引用所有關鍵反例 |
| 誤判與審核 | Oracle False Reject／False Accept 的分子分母、爭議、Independent Semantic Approval；輸入核准與輸出審查分開，綁定確切 hash |
| 成本與風險 | Calls／Tokens／Latency、未知用量；工程建置、維護、升版、部署與新 ERP／客戶導入工時，實測與估算分開；語意及授權待審風險 |
| 後續 | 建議、待驗證項與責任人／任務 ID、需要業務審核的前提、實作是否另獲授權、回退／遷移要求、對 S4～S6 的影響 |

每份紀錄區分「報告完成」、「候選能力通過」、「獨立語意核准」及「產品階段驗收」。任何一欄不能推導其他欄已通過。證據缺漏保留 null／未測及原因，不能補造已執行命令或簽核。

## 實驗判定規則

1. 執行前登錄比較矩陣、固定分母、候選責任、模型設定與差異、指標／安全門檻及 Pilot／擴大範圍。研究閾值尚未核准時標 Open Question；不得以執行結果倒推門檻。
2. 六層成績分開呈現，不單靠總 PASS rate、單題通過或 Package 宣稱有功能決定選型。多模型／多知識量組合不可假稱公平的單變因比較。
3. 無法提供某輸出格式不直接判 FAIL；看其是否履行相同業務語意義務。確實不承擔該責任則標不可比；不得移除失敗案例或事後改 scope 縮分母。
4. 合法等價方案與規則變更先獨立審核，給新版本與新決策 ID；保留原判定／Raw／grader。不同版本重評寫新目錄，用 `supersedes` 關聯，不能覆寫原成績。
5. Replay PASS 只代表重現／離線驗證；不代表新的自然成功。Raw replay、response regrade、fixture 執行及完整自然 trial 分開列。

## ADG-01：S2 前架構設計決策

輸入是 R1-A、R1-B、R2-03 可審核報告，含 S1-08-BL 與現有產品限制。負面／受阻報告可以完成研究交付，但不能冒充候選通過。四種結論均須填共通欄位並引用實測；缺乏必要證據時使用不足結論。

| 結論 | 適用條件與後續 |
| --- | --- |
| `KEEP` | 依已測範圍與失敗／成本證據保留現有規劃；列未解決語意風險、仍需修正與重評觸發條件，不代表現有系統全數通過 |
| `ADAPT` | 證據支持某能力部分替換／Package 重用；列責任邊界、保留治理／gate、遷移／相容／回退及新增驗收，另行核准實作 |
| `REPLACE` | 同等完整責任的比較與獨立審核足以支持替換主要引擎；完整列失敗、缺口、成本及遷移前置，不能只憑單題、靜態 Join 或套件功能列表 |
| `INSUFFICIENT_EVIDENCE` | 證據量、可比性、離線能力或審核不足；暫延續既有方案並保留風險／後續驗證，不推定現有或外部方案勝出 |

**Gate 是設計決策，不是產品測試豁免。** S2 進入條件為「ADG-01 已完成且有明確後續處理」**以及**原 S1-01～S1-08 全部驗收成立。自然 baseline FAIL 可觸發 R1，不能使 S1-08 轉完成；R1、R2、ADG-01 的完成欄亦不能更改它。若決策要求遷移，先取得獨立實作授權並通過原驗收／新相容性要求，不能在記錄決策時自動切換入口。

若不足結論仍有未解安全風險，須列出對 S1／S2 的阻擋；僅「已填結論」不消除既有產品 Gate。研究提出修改驗收範圍時須另提修訂供使用者確認，原規格在確認前仍有效。

## R3 決策與 S4～S6 回饋

R3 使用同樣四種結論詞彙及獨立紀錄 ID，不覆寫 ADG-01。必附固定 fixture 的靜態／實際結果對照、Join Cardinality／母體／Aggregation／NULL／零／無列／完整性與重複指標證據，區分相同 DB、跨 DB 及未測方言。外部完整 Join 不與 S1 多份獨立 SQL 做結果層勝負比較。

R3-03 逐項交接：S4 的 typed binding、DAG 與來源／版本失效；S5 的 provider／規劃／DB／整合錯誤、pending 與恢復；S6 的 requirement／claim evidence、部分成功、成本與自然驗收。每項列採納／保留／待確認及對應規格位置。若研究結論不足，列後續工作與風險，不自動免除 R3 的結果驗證或 S4～S6 原產品驗收。
