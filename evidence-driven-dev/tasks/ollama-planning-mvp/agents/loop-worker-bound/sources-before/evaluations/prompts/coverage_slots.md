# 具名需求槽位

依完整原始request、全部requirements與當次單一View契約判定每項需求。只輸出符合response_schema的原生JSON，不輸出Markdown或SQL。entries是具名物件：每個key必須逐字使用schema給定的requirement ID，全部必填且各出現一次，不能重複key、增減項目、改用清單或按位置配對。

每個槽位只填status、mappings、contract_path、missing_requirements；不得再輸出requirement_id。View身分、來源grain.description、完整grain.keys及來源population由Python從唯讀契約取值，population逐字使用summary並附/summary證據；不得輸出或覆寫這些來源事實。summary原文不是新推導的母體保證，不得推論契約未明示的退貨排除、通路或其他能力。

# 模型判定責任

逐項判斷status、合法欄位mappings、同源scope及缺口，仍須你自行負責。supported須有mappings、有效contract_path、空missing_requirements，且scope_ids在同一View全部supported；否則保留合法部分映射並標partial。unsupported／uncertain的mappings為空，所有非supported項目須有missing_requirements。即使契約有店商品鍵，也不能因此判定完整庫存母體supported；只有銷售資料的來源不能宣稱包含未售庫存。後續仍須驗證anchor、篩選及left合併保母體。

contract_path只能是指向契約非空字串的一個JSON pointer，不回傳quote、source_quote或contract_evidence。grain需求只能用/grain/description；其餘可用/summary或相關/columns/欄位名稱/description；沒有相關文字的unsupported／uncertain可用null。Python依路徑取得原文，不替你修正status或缺口。

mapping只填column、role、aggregation、operator、value與conditions。每個mapping的需求原文及自身欄位description由Python取文。grain／population僅用key映射識別鍵，不能夾帶篩選。metric須有合法aggregation；其他角色aggregation=null。filter須有operator與型別正確value；其他角色operator=null、value=null。conditions通常為[]，僅條件度量可用且條件欄位須有獨立filter映射。度量及日期／通路scope必須由同一View支持，不能向別的View借欄位。metadata須映射真實來源欄位，不把純業務目的背景轉成欄位，也不把資料日期當分組維度。
