
# ERP AI Assistant — Text-to-SQL 第一階段開發計畫

**開發期間：2026/10/15～2026/11/14（1 個月）**

**開發目標：** 建立可安全直連企業資料庫、理解複雜需求、拆分查詢任務、整合結果，並產生可驗證回答的 Text-to-SQL 系統。

**開發原則：**
- 延續現有系統功能，不重新開發已完成的能力。
- 優先補足複雜需求拆分、結果整合與正確性驗證。
- 以企業安全性、可靠性及可用性作為驗收標準。
- 本階段以受控 PoC 為目標，不包含正式商用部署。

---

## 第一階段：10/15～10/21
### 基礎能力確認與企業資料庫存取安全

**功能**
- 企業資料庫直連。
- 自然語言查詢與多表資料分析。
- 資料結構與業務欄位識別。
- 查詢結果與執行紀錄追溯。

**必須完成事項**
- [ ] 確認現有 Text-to-SQL 功能及限制。
- [ ] 完成資料庫連線與權限控管驗證。
- [ ] 確認系統可理解資料表關係及業務欄位。
- [ ] 建立既有功能的正確率與效能基準。
- [ ] 建立可重複使用的標準測試案例。

**風險控制注意事項**
- 禁止 AI 未經授權修改資料庫內容。
- 使用獨立、最小權限的唯讀帳號。
- 防止越權查詢及敏感資料外洩。
- 避免大量查詢影響客戶 ERP 正常運作。
- 客戶正式資料庫存取須經授權，優先使用測試環境。

**對企業價值**
- 降低員工查詢資料時對 IT 人員的依賴。
- 減少跨表查詢及整理資料的時間。
- 在不更換 ERP 的前提下提供自然語言查詢能力。

**必要驗證項目**
- [ ] 一般查詢正確率 ≥ 90%（至少 20 題）。
- [ ] 未授權讀取及資料修改均被阻擋。
- [ ] 多表查詢與關聯結果正確。
- [ ] 查詢失敗、逾時及空資料能正確回報。
- [ ] 查詢操作可追溯且不洩漏敏感資訊。

## 第二階段：10/22～10/28
### 複雜需求理解與任務拆分

**功能**
- 辨識複雜查詢需求。
- 將複雜需求拆分為多個子任務。
- 辨識任務之間的依賴關係。
- 判斷需求是否存在模糊條件或資料不足。
- 規劃多步驟查詢流程。

**必須完成事項**
- [ ] 能區分簡單與複雜需求。
- [ ] 能將複雜需求拆分為合理且完整的子任務。
- [ ] 能判斷各子任務的執行順序與相依關係。
- [ ] 能辨識需求中缺少的必要資訊。
- [ ] 確保拆分後的任務沒有遺漏原始需求。
- [ ] 建立至少 25 題複雜需求測試案例。

**風險控制注意事項**
- 避免錯誤理解業務名詞及計算條件。
- 避免過度拆分導致效能與資源浪費。
- 不可為完成子任務而擴大資料存取權限。
- 不得擅自假設重要的財務、庫存及營運指標。
- 資料不足時應提出澄清，而非自行推測。

**對企業價值**
- 使用者不必具備 SQL 或資料庫專業知識。
- 降低複雜資料分析對資深 IT 人員的依賴。
- 支援跨部門、跨時間、跨資料表的分析需求。
- 減少員工自行拆解問題及反覆操作 ERP 的時間。

**必要驗證項目**
- [ ] 25 題複雜需求中至少 20 題正確拆分。
- [ ] 子任務涵蓋使用者原始需求。
- [ ] 任務依賴關係及執行順序正確。
- [ ] 無重複、循環或無關的查詢任務。
- [ ] 模糊需求能正確辨識並要求澄清。
- [ ] 不會因任務拆分而繞過資料權限。

## 第三階段：10/29～11/04
### 多任務執行與結果整合

**功能**
- 依照任務規劃執行多個查詢。
- 整合不同查詢所取得的資料。
- 支援跨期間、跨部門的數據比較與分析。
- 驗證資料一致性及計算正確性。
- 產生整合後的自然語言回答。

**必須完成事項**
- [ ] 能依任務依賴關係完成多步驟查詢。
- [ ] 能正確整合不同查詢的結果。
- [ ] 能處理數據比較、彙總、排名及條件篩選。
- [ ] 能辨識資料缺失、重複與不一致情況。
- [ ] 回答中的重要數據能追溯至原始資料。
- [ ] 能正確處理部分查詢失敗的情況。

**風險控制注意事項**
- 避免多表關聯造成數據重複計算。
- 不得將不同單位、期間或統計口徑的數據錯誤合併。
- 不得將空資料直接解釋為數值 0。
- 不得將部分成功的結果宣稱為完整結果。
- AI 不得自行捏造缺少的數據。
- 限制多任務執行所產生的資料庫負載。

**對企業價值**
- 減少員工手動合併 Excel、SQL 報表的作業。
- 加速跨部門營運資料的整合與分析。
- 協助管理者理解複雜業務問題。
- 降低人工彙整造成的錯誤風險。
- 建立後續營運異常分析與決策輔助的基礎。

**必要驗證項目**
- [ ] 複雜需求端到端正確率 ≥ 80%（至少 25 題）。
- [ ] 重要計算結果與人工驗證結果一致。
- [ ] 不會因資料關聯產生錯誤重複計數。
- [ ] 資料不足與查詢失敗有明確提示。
- [ ] 最終回答可追溯其查詢來源與計算依據。
- [ ] 不會將未經驗證的推測呈現為資料事實。

## 第四階段：11/05～11/11
### 企業使用驗證與可靠性測試

**功能**
- 查詢結果與分析過程人工覆核。
- 複雜及模糊需求的錯誤處理。
- 查詢品質與系統效能評估。
- 查詢歷程及異常紀錄。
- 企業業務情境測試。

**必須完成事項**
- [ ] 提供可供人工核對的查詢及結果紀錄。
- [ ] 完成複雜問題的端到端測試。
- [ ] 建立錯誤案例及問題分類。
- [ ] 完成安全性與查詢負載測試。
- [ ] 建立至少 3 個企業業務情境。
- [ ] 量測原有人工流程與 AI 協作流程的差異。

**風險控制注意事項**
- 防止錯誤數據被直接用於重大營運決策。
- 避免 AI 過度自信地回答不確定問題。
- 防止敏感資料出現在查詢紀錄或外部服務。
- 控制高負載查詢對 ERP 資料庫的影響。
- 確保系統發生錯誤時不影響原 ERP 運作。

**對企業價值**
- 提高資料查詢及分析結果的可信任程度。
- 降低 AI 導入所需承擔的營運風險。
- 提供資訊部門可追蹤、可管理的系統。
- 建立 AI 導入效益的客觀評估依據。
- 降低正式導入前的不確定性。

**必要驗證項目**
- [ ] 至少 10 題模糊需求測試，9 題以上適當處理。
- [ ] 至少 15 項安全測試全部通過。
- [ ] 人工能追溯核心查詢與分析結果。
- [ ] 能量測端到端回應時間及主要效能瓶頸。
- [ ] 主要業務案例能完整執行及驗證。
- [ ] 安全測試不得有未解決的高風險問題。

# 最終驗收標準

| 驗收面向 | 最低要求 |
|---|---|
| 簡單查詢 | 20 題至少 18 題正確 |
| 複雜需求拆分 | 25 題至少 20 題正確 |
| 複雜需求端到端 | 25 題至少 20 題正確 |
| 模糊需求處理 | 10 題至少 9 題適當處理 |
| 安全與權限 | 15 項測試全部通過 |
| 數據可信度 | 核心數值均可追溯來源 |
| 系統可靠性 | 錯誤、逾時及失敗均能安全處理 |
| 業務驗證 | 至少 3 個完整應用情境 |
| 商業價值 | 有人工與 AI 流程的效率比較 |

以上為開發期 PoC 的初步門檻，測試題目應包含未參與開發調整的案例；正式商用所需的準確率、安全與效能標準，應再依客戶及業務風險提高。

# 本月完成後的產品定位

**企業級 Text-to-SQL 分析引擎（PoC）**

具備：
- 安全存取企業資料庫。
- 自然語言查詢。
- 複雜需求理解與拆分。
- 跨資料表及多任務查詢。
- 數據驗證與結果整合。
- 可追溯的 AI 分析回答。
- 人工驗證與品質評估。

**下一階段方向：ERP AI 主動營運異常分析**

將使用者主動提問的模式，逐步擴展為系統主動偵測異常、解釋原因、提出建議及追蹤處理結果的企業 AI 協作助手。
