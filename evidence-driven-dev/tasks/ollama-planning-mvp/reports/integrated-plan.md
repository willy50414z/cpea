# DeepSeek 優先的需求拆分 MVP 整合方案

本次已完成背景整理及實際 subagent 設計委派；以下是待實作、待實測的方案。**先讓 Azure DeepSeek-V4.1-Flash 通過完整驗收，再以相同契約與門檻測 Ollama qwen3.8:27b。** 本輪沒有新增模型呼叫、生成或執行 SQL、查詢資料庫，也沒有修改產品程式。

## 背景與證據

[背景摘要](background-brief.md)共 999 字元，含標點與英數，不含檔尾換行。既有七個 View、30 題跨來源需求的單次規劃，同時處理來源、欄位、條件、粒度及整合；目前仍使用原版 prompt v3。

| 既有完整首輪，皆非完整語意核准 | GPT | DeepSeek | Ollama Qwen |
|---|---:|---:|---:|
| 來源與必要欄位原分 | 30/30 | 26/30 | 21/30 |
| Request 就緒 | 30/30 | 22/30 | 11/30 |
| 自動結構通過 | 30/30 | 18/30 | 7/30 |

來源：[既有模型結果](../../retail-task-decomposition/reports/ollama-results.md)。Qwen 的欄位原分包含四個已知漏判；request 就緒不保證母體、條件或粒度正確。問題包含漏宣告使用欄位、選錯來源能力、母體被 inner join 刪除，以及根粒度與子集合混淆，不能歸因為資料庫單純缺欄位。

既有 DeepSeek 十題原版／加檢查步驟／三階段規劃，自動通過為 7／2／2，三階段曾固定並傳遞錯誤粒度。完整改寫 prompt 與能力展開、最小候選映射 prompt 均未通過原先採用門檻，已撤回。參考[分階段負結果](../../retail-planning-stages/reports/results.md)及[prompt 實驗](../../retail-planning-stages/reports/prompt-view-matching-results.md)，保留原分與全部失敗。

## 主 agent 整合建議

實際 subagent 的[完整提案](subagent-proposal.md)比較三個候選：A 保留一次規劃並加入確定性欄位閉包與護欄；B 由模型輸出較短的語意骨架，再編譯為現有 draft；C 多階段 LLM 加邊界驗證。先以 A 做零呼叫實驗；若只能改善格式，便把 A 保留為護欄，再測 B。C 須有節點證據支持才測，不能直接重做既有失敗拆分。

模型負責需求覆蓋、來源語意、條件、母體、根與子粒度、整合意圖；程式只導出可證明的重複結構。欄位閉包只能收集已明列且符合來源能力的欄位角色，不能猜測模型漏掉的業務要求。不能自動改母體、刪月份、把 inner 改 left 或選 nest／aggregate 來追求通過。

先保留全部七個 View。若未來裁剪，須按子需求召回並取候選聯集，驗證全部必要來源同時被召回，不能要求每個 View 單獨滿足整個跨來源需求。

| 階段 | 執行與產物 | 升級條件 |
|---|---|---|
| MVP0：離線定位 | 重播 DeepSeek 已存回覆；保留原分，另列欄位閉包及語意檢查；建立錯誤反例與合法等價控制 | 重播一致；不安全計畫不能被修成 ready；確認哪些問題能由程式確定處理 |
| MVP1：DeepSeek 小樣本 | 六題開發集，候選與新鮮 v3 同場配對；B 先做人工核准骨架的編譯測試，再測自然抽取 | 必須有語意安全改善、成功控制無重大退步；不把人工注入成功當模型抽取成功 |
| MVP2：DeepSeek 擴展 | 十題新測試，含澄清／拒絕負例；至多一次有限修正，初次與修正後分開報告 | 達完整提案的預先門檻，且零不安全 ready；失敗先修假設，不重跑挑答案 |
| DeepSeek 完整 Gate | 固定版本驗收原 30 題＋8 題封存控制，逐題語意審查，完整跑兩輪 | 每輪首次結果 38/38 正確，來源、欄位、條件、粒度、母體、缺值及 payload 全部通過；應澄清／拒絕者正確回應；無待審項目 |
| Ollama 移轉 | 只有上述 Gate 通過才呼叫 Qwen；凍結語意契約、編譯器、規則與驗收案例，從小樣本開始 | 最終同樣兩輪各 38/38；完整記錄 provider、JSON 約束與生成設定差異，不用調低標準換取通過 |

呼叫、token、時間與停止條件見完整提案。這些是未來實驗的預算與停止規則，不恢復使用者已解除的 Azure 呼叫額度限制，也不另加逐階段人工核准要求。若既有實作授權覆蓋後續工作，可依門檻自行推進。

## 驗收界線與審查要求

「完全正確」指上述固定案例與契約範圍通過，不代表任意需求皆有保證。原題不能以 27/30、request ready 或原 grader 的 30/30 替代完整 Gate。每次結果須分開報原始自動分、嚴格語意分、初次及修正後結果。若修正評分盲點，必須版本化並同樣重評各 baseline，原始分數持續保留。

封存新題的預期應在看到模型回答前固定；揭露後再用於調整就屬開發資料，需補新的封存組。重複測試仍是小樣本穩定性觀察。人工語意審查須提供契約依據、等價邊界與反例，尚未核准的項目不能算通過。

若人工審查發現原題的 ready 預期與 View 契約矛盾，須先記錄並解決預期爭議，保留原版本及分數；不能強迫產生不合法 request，也不能在看到候選失敗後偷偷改成可拒絕來算全對。

本次主 agent 已核對既有報告、現行 validator 與 subagent 候選的安全前提。文件交付驗證與模型能力驗證分開；**新方案能否改善正確率仍為 NOT_VERIFIED**，既有 391 passed／1 skipped 是原產品版本的歷史測試結果。
