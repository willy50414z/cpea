# 三階段 View 選擇與需求映射執行計畫

> 執行者依本計畫逐項完成核取項目；實作時使用 `superpowers:executing-plans`，延續主 agent 直接執行方式。原撰寫回合只記錄計畫；本輪依使用者新授權執行，結果另列報告。

**日期**：2026-10-21（Asia/Taipei）。

**狀態**：2026-10-21 已依新授權實作 evaluation 候選；第11題診斷未通過，端到端語意 NOT_VERIFIED，不能宣稱提高 DeepSeek 正確率。見[執行結果](three-stage-view-selection-results.md)。下列預算與門檻保留為原計畫依據。

**目標**：先召回可能相關的 View，再逐 View 建立有契約證據的部分需求映射，最後選出完整滿足需求且可正確整合的必要來源。

**架構**：重用現有 text-to-sql 的候選檢索、契約與欄位驗證能力；新增跨 View 的部分支持模式及來源組合選擇。先放在 evaluation 候選，保留產品 v3 預設。

**技術**：既有 Python、Pydantic、SchemaCatalog、DeepSeek-V4.1-Flash、typed decomposition／prepared request 契約。

**設計依據**：本次三步討論、[既有整合方案](integrated-plan.md)及[原始分階段提案](subagent-proposal.md)。最新負結果見[優先序實驗](coverage-priority-comparison.md)與[Markdown／第二模型審查](markdown-evidence-review.md)。

## 全域限制與驗收焦點

- 完整需求覆蓋優先於來源數、粒度便利、彙總工作量及成本。
- 不產生或執行 SQL、不查 DB；本計畫停在合法子任務 request 準備。
- 保留所有首次 raw、分數與失敗；模型理由只作可核對摘要，不要求私有逐步思維鏈。
- 不把較強模型或第二個 DeepSeek 當 oracle；原始生成與審查成績分開。
- 不因三步拆分而預設三次呼叫；完整記錄每個節點的 tokens、時間與費用依據。
- DeepSeek 原30＋封存8題，固定版本兩輪首次各38/38語意正確，仍是進入 Ollama 的必要門檻。
- 所有文字檔使用 UTF-8 無 BOM；Markdown 使用繁體中文。

重點檢查：候選召回漏來源、單表部分映射被提前丟棄、虛構欄位、跨來源錯套條件、錯誤母體／粒度及無證據的合併假設。

## 第一步：整理需求並召回候選 View

**輸入**：原始完整需求、核准 View 清單與契約。

**輸出**：

- `requirements`：穩定的 requirement_id、原文片段、業務對象、欄位角色、條件／期間、粒度與保留母體。
- `candidate_views`：可能相關來源及召回依據；不在此決定最終資料來源。

模型負責辨認業務語意；程式驗證原文片段、來源名稱與引用存在。必要資訊含顯示欄位，也含未顯示的篩選欄位、識別鍵及資料時間。

首個 MVP 保留現有全部七個 View，讓實驗先隔離逐來源映射與最終選擇問題。未驗證必要來源集合召回率前，不啟用 top-k 裁剪；未來若裁剪，按子需求召回後取聯集。不得要求每個候選單獨滿足整個跨來源需求。

## 第二步：逐 View 映射需求，保留部分支持

**輸入**：同一份原始需求、第一步的全部需求項目，以及當次一個 View 的完整契約。

**輸出**：每個 View 的 `ViewCoverage`，至少包含：

| 欄位 | 意義 |
|---|---|
| `view`、`requirement_id` | 支持哪個業務需求，避免只比欄位名稱 |
| `status` | supported／partial／unsupported／uncertain |
| `mappings` | 實際欄位、角色、條件值、聚合及原文依據 |
| `contract_evidence` | 可解析的契約路徑及原文引文 |
| `grain`、`keys`、`population` | 來源能力、可用對齊鍵及母體限制 |
| `missing_requirements` | 缺少哪些條件、欄位或必要語意 |

每個候選逐一處理；不因無法回答整題而刪除合法的部分映射。不存在欄位、非法聚合或不成立的契約引文，由程式直接標為不合法，不讓模型自述補成證據。

**度量與適用條件必須一起驗證。** 「九月線上銷售額」是帶期間及通路範圍的需求；只有金額和月份、沒有通路的 View，只能標部分支持。不能用另一來源的通路欄位替已混合通路的月彙總金額補上篩選能力。

## 第三步：選必要來源並形成可驗證分工

**輸入**：完整需求、所有經程式檢查的 ViewCoverage，以及原始來源契約。

**輸出**：最終來源集合、每項需求的負責來源、選擇／排除依據，以及現有 DecompositionDraft 所需的子任務與整合意圖。

選擇順序：

1. 所有必要需求均有合法來源能力；partial 不得冒充完整支持。
2. 確認度量口徑、條件作用來源、資料時間、粒度、母體、合併鍵及基數相容。
3. 在符合前兩項的組合中，再移除無必要來源及比較整合成本。

程式可處理欄位存在性與可證明的冗餘，不得猜測遺漏條件、任意改粒度或把 inner 改成 left 追求通過。第三步不得新增第二步未驗證的欄位或來源能力；證據不足就明列缺口。

來源選完後仍須驗證各子任務 filters／metrics／attributes／metadata、output_grain、integration、缺值政策及 request。沿用既有 validator／request preparer；`ready` 不等於語意正確，不能只靠欄位集合覆蓋率放行。

## 與現有 text-to-sql 的重用邊界

| 現有能力 | 本候選的使用方式 |
|---|---|
| `_retrieve_schema` | 重用檢索與 context budget；初版全七來源作控制 |
| `_match_candidates` | 參考逐 View 完整契約映射與來源限定 schema，不直接沿用整題成功才選中的路由 |
| ClauseMapping／契約驗證 | 重用欄位角色、運算子與聚合能力檢查；外包一層部分需求覆蓋記錄 |
| 語意驗證 | 保留原文、欄位含義與資料粒度檢查，新增跨來源需求綁定檢查 |
| task decomposition validator／preparer | 最終驗證與 request 準備；本輪不呼叫 SQL compiler 或資料庫 |

現有單表 matcher 無法完整支持需求時會拒絕；跨來源候選必須保留合法的部分支持，不能只替換 prompt 而忽略這項介面差異。既有單表流程不改成允許缺漏的查詢。

## 第11題的預期診斷產物

需求：對照各店各商品目前庫存件數與2026年9月線上通路的折扣金額及淨銷售額，保留所有庫存商品。

| View | 能力與缺口 | 第三步用途 |
|---|---|---|
| `v_inventory_status` | 庫存、店商品識別鍵及盤點日期；不負責歷史線上銷售條件 | 庫存母體 |
| `v_product_monthly` | 月份、折扣、淨銷售額；缺通路欄位 | 不選作本題線上銷售金額來源 |
| `v_sales_detail` | 月份、通路、折扣、淨銷售額及店商品鍵；需先篩選再彙總 | 銷售子任務 |

此表只作離線預期／測試依據，不寫入 runtime prompt。執行時仍提供全部核准契約，由候選自行映射及選擇。

## 模型呼叫與成本界線

三個邏輯階段不等於三次模型呼叫。若需求整理1次、每個候選各映射1次、最終選擇／分工1次，N個候選共N＋2次；七個 View 即每題9次。若另加第二 DeepSeek 審查，再增加1次；審查先保留為可選診斷，不自動加入每題。

六題候選加 fresh v3 配對預計需6×9＋6＝60次，**超過原單次候選方案的12次六題預算**，不能直接套用舊上限啟動。後續執行前須在新 EXP 寫明實際呼叫、token、時間、成本與停止預算；原撰寫回合沒有啟用預算。本輪EXP-009／010僅啟用第11題合計最多9次，未啟用六題60次。

逐 View 的需求與契約不無聲裁切；模型建構前檢查 context budget。首版序列執行，保存各節點成本／耗時；即使同樣使用低成本模型，也須比較端到端成本與原一次規劃。provider 錯誤停止，額度限制依現有帳號規則處理，不自動重試。

## 分階段門檻與停止條件

| 階段 | 必要證據／升級門檻 |
|---|---|
| 離線控制 | 所有需求有覆蓋紀錄；非法欄位與假契約證據不能流入 ready；合法部分映射保留；已存結果可重播 |
| 第11題診斷 | 自然生成來源、通路／期間、金額、粒度、庫存母體與 request 正確；人工注入映射只證明程式能力，不能算模型成功 |
| 六題 | 沿用原提案的語意品質門檻：至少5/6安全ready，或相較同場v3淨增至少2且達4/6；02、07控制無真語意退步；零不安全ready；來源／母體／根粒度節點至少5/6正確。另單列新三步的來源召回與映射覆蓋指標 |
| 十題 | 使用已核准的新案例，依原提案預先門檻驗收；負例及不安全ready分開，不以ready數量替代語意正確 |
| 完整 DeepSeek／Ollama | 維持原30＋封存8、固定版本兩輪首次各38/38；DeepSeek未過不呼叫Ollama |

任何不安全 ready、必要來源遺漏、假證據通過、預算耗盡或版本不一致，均停止該階段並記錄原因。第一個出錯節點應先形成可否證假設；不得在下游直接修補答案掩蓋上游失敗。修正版與首次結果分列，封存案例不參與調整。

本計畫的假設是「逐來源、帶需求範圍與契約證據的部分映射，可能改善來源選擇並讓錯誤更易定位」。既有三階段及B1曾失敗，拆分本身不是有效性的證明；本候選必須以自然生成的端到端結果驗證。
