# Retail 拆分錯誤修正與驗證

固定版本：`bc09c67`。依使用者最新指示停止 GPT 第二輪，改用 Azure `DeepSeek-V4.1-Flash` 執行完整第二輪。兩模型沿用完全相同的30題、prompt v3、schema、View契約及評分規則。

## 根因與修正

1. **日期欄位政策不一致。** v1稱快照日期「可保留」，題庫卻要求必備；彙總日期也只有裸attribute，不能表達日期集合。修正為保留來源時間，逐筆用attributes，彙總用明確的metadata_collections，完整DISTINCT集合傳入prepared request，不能宣稱混合日期為同日快照。
2. **分析粒度被額外欄位分裂。** 模型自行加入未要求的門市／商品名稱、SKU、盤點日。通用規則改為需求維度及必要識別鍵；不假設未在契約中證明的函數相依。
3. **整合評分不一致與邊界驗證不足。** 子任務接受來源唯一鍵證明的冗餘欄位，final卻拒絕；修正兩端均要求保守證明。final不得夾帶未查出的欄位或靜默縮減未證明維度；必要時明列nest/pivot/aggregate。
4. **Oracle與條件表示。** 獨立審查確認26應篩選明示雙通路；14的stock_qty只供條件，不應列為店級單值attribute。聚合日期改集合有明確語意。保留conditional metric與一般度量差異、零符合與未匹配差異的反例，不任意放寬答案。
5. **V2新增通路回歸。** 未指定集合的「各通路」被模型限縮為契約例值；v3明示範圍只能來自使用者，例值不是封閉域。

## DeepSeek失敗與額外語意風險

保留原始自動18/30，不針對本模型改題庫或分數。獨立審查12個自動未通過項目：

- 合理等價表示3題：04分開查兩個月份；06月欄位日期範圍與首日等值；17註冊日期包含月末與排除次月首日。現grader未涵蓋，仍保留原分。
- 意圖合理但輸出契約不一致4題：10、16、22、24，分組／粒度／nest keys等不一致，被validator拒絕，不能算request就緒。
- 真正來源、母體或欄位錯誤4題：11使用不支援通路的月表；14先篩掉非缺貨庫存而漏掉零缺貨門市；26幻造order_count且漏通路條件；29以不支援通路的商品月表聲稱線上銷量，且分組違約。
- 多餘澄清1題：21可直接讀取既有active欄位，卻要求非需求中的期間定義。

自動通過也有語意盲點：05額外要求stock_qty跨盤點日加總，日期集合不能作為同日證明；15、19在未證明函數相依下使用彙總單值名稱；08、25部分必要值只列required_columns，未以輸出角色明示。故18/30不是已完成人工語意核准的正確率，也不代表所有ready計畫可安全執行。仍未生成或驗證實際SQL。
